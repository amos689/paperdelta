# 持续审查中的增量检查

[English](../v1.9.md)

1.9 在 `paperdelta watch` 和 Studio 会话中复用未变化的文档解析与精确指标结果。
每次检查仍读取当前文件并计算内容哈希。普通 `paperdelta check` 继续完整重检，
也是验证增量路径是否正确的对照。

```sh
paperdelta --lang zh-CN watch --baseline submitted-v1 --report build/paperdelta
paperdelta --lang zh-CN watch --no-cache --baseline submitted-v1 --report build/full-check
paperdelta --lang zh-CN studio
```

## 哪些变化使缓存失效

文档身份包括解析后的项目根目录、相对文件名、精确内容哈希、格式及对应宏/区域配置。
LaTeX 包含文件发现和歧义检查每次重新执行，也会发现此前缺失而新建的文件。
证据身份包括完整的类型化来源声明及当前内容哈希。来源指标还包括精确筛选条件、
单位和统计约定。派生指标依赖完整上游结果，包括原始证据位置。
因此 CSV 行重排后，即使均值相同，来源行号也会更新。

一个来源变化时，其他来源的指标可以继续复用；一个大来源文件发生修改后，所有依赖
该文件的指标失效。本版不承诺逐行增量解析。最终报告、论文绑定、论断、覆盖、图形、
生成记录、复核记录和基线比较仍重新计算。输入缺失或损坏会产生当前错误，
不会用缓存替代读取失败的文件。

检查结束前再次读取输入身份，检测检查过程中发生的变化。持续检查保留既有防抖和
等待状态；输入尚未稳定时，旧的通过报告不会被表示为当前结果。
已有预览和确认继续执行各自的输入新旧验证。

## 内存、副本与兼容

每个持续会话使用进程内 LRU 缓存，默认最多 4,096 项，以及保守计量的 64 MiB 保留对象。
单项超过 16 MiB 时不缓存。计量包含 Python 容器及 Word 原生 XML 树，无法可靠计量的
原生对象同样绕过缓存。大型 CSV 的完整解析可能不缓存，但体积更小的精确指标结果
仍可复用。上述上限针对缓存保留对象，不代表整个进程 RSS、临时解析内存或 Python
分配器保留内存也受同一上限约束。

缓存项与返回结果使用隔离副本，PDF/Word/Markdown 表格元数据会重新关联副本中的
行身份。修改展示出的报告不会污染后续检查。Markdown 解析完成后释放不再需要的
解析器闭包。缓存不保存文件句柄、可执行论文代码、接受决定或磁盘文件。

缓存身份包含当前工具、Python 与解析依赖版本、语言和十进制上下文。重启或升级后
缓存为空；改变引擎身份或显式清空缓存也会重新解析，不需要迁移缓存文件。
配置 schema 10、报告 schema 9、既有命令及原生位置身份保持兼容；兼容的 1.8 草稿
经重新验证后可以恢复，恢复不会自动接受。

## 验证与测量

回归仅排除 `created_at` 后逐项比较完整报告，覆盖冷/热缓存、五种稿件格式与两种语言、
五种证据格式、大小/修改时间不变的内容替换、来源删除恢复、CSV 重排、筛选条件、单位、
缺失/歧义包含文件、基线、复核记录、解析器身份、语言、十进制上下文、有界淘汰以及检查
过程中的输入变化。

使用新的输出目录复现原创负载测量：

```sh
python tools/validate_incremental.py --out build/incremental-check --runs 20
```

可选参数 `--reference-python /path/to/previous/python` 使用实际安装的上一版检查同一输入。
工具测量 20 个 LaTeX 文件、10 MB CSV、500 个绑定，以及 8 页 PDF、320 个绑定，
交替执行完整与热缓存检查，报告冷启动、median/P95、内存计量和十种失效场景，逐项
比较报告。跨版本比较另外排除 `tool_version`。这些是受控机器测量，不是独立真人
易用性结果，也不保证任意论文具有同样延迟。

最终安装包、浏览器和公开下载验收已记录在[交付路线图](roadmap.md)。
按本项目次版本逢十进一的约定，下一版已批准的 Agent 升级版本为 **2.0**。

多个来源声明引用同一文件时，一次检查内读到的哈希也必须一致；不同快照会明确产生
`INPUT_CHANGED`。证据读模型构建完成后释放重复的原始字节和文本缓冲区。

工作流检查会延迟真实的修改前报告响应，并等待已编辑 CSV 的哈希；
仅“检查代次增加”不足以证明新文件已读取。

在 Windows 11 / Python 3.12.14 / Intel Core Ultra 9 275HX 上，
实际安装的 1.8 和 1.9 对相同自建输入每种模式各测量 20 次：

| 负载 | 1.8 完整检查 P95 | 1.9 完整检查 P95 | 1.9 热缓存 P95 | 1.9 单次冷缓存 |
| --- | ---: | ---: | ---: | ---: |
| 20 个 LaTeX 文件 / 10 MB CSV / 500 个绑定 | 1.729 s | 1.759 s | 0.853 s | 1.927 s |
| 8 页 PDF / 320 个绑定 | 1.265 s | 1.265 s | 0.246 s | 1.262 s |

大 CSV 的冷检查需要承担缓存构建成本，本次优化主要面向持续审查中的重复检查。
大项目和 PDF 的缓存保留对象计量分别为 6,892,499 和 2,219,161 字节，均在 64 MiB
预算内；测量后的进程 RSS 分别为 207,343,616 和 208,175,104 字节，峰值为
267,542,528 字节。缓存预算不是整个进程的内存上限。
每种负载的 20 组完整／热缓存报告、上一版结果及十种失效场景的全部比较字段一致。
