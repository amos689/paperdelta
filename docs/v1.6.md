# PaperDelta 1.6: from experiment outputs to a revision list

[简体中文](zh-CN/v1.6.md)

Version 1.6 adds reviewed Notebook/Quarto generation records, generated LaTeX and
Markdown result fragments, and a revision list joining numeric statements,
claims, figures and rendered outputs. It keeps explicit evidence identities and
the existing five manuscript formats. Notebook support inspects saved cells and
declared files; it does not treat arbitrary notebook output as accepted evidence.

## Inspect a saved Notebook

```sh
paperdelta provenance notebook analysis.ipynb
```

Inspection is local and read-only. It shows stable cell IDs, source/output hashes,
saved execution counts and saved errors. Modern nbformat 4.5+ IDs must be unique;
older notebooks without IDs use explicit `index:N` identities. Missing execution
counts, saved errors and unsupported output types stay unverified. Saved outputs
and counts do not establish that code actually ran, in what order, or with every
required input. MIME content is hashed, never executed or rendered by inspection.

## Declare and review a generation relationship

```sh
paperdelta provenance preview training --kind notebook --source analysis.ipynb --cell metrics --input observations.csv --input run_notebook.py --output results/metrics.csv --rationale "Reviewed selected cell and listed dependencies" --out training-plan.json
paperdelta provenance accept training-plan.json
paperdelta check --report build/review
```

Review the plan before the explicit `accept` command. Repeat `--cell`, `--input`
and `--output` for additional declared files/cells. Notebook declarations require
at least one code cell; Quarto declarations do not use `--cell`. For a render,
use `--kind quarto --source paper.qmd --output paper.pdf` and explicitly list
relevant data, figures, templates and other dependencies with `--input`.

Acceptance backs up the configuration and stores a content-identified record.
Reusing a name requires `--replace` in a new preview. Changed source, selected cell
code, saved output, execution count or listed file invalidates freshness. A missing
or unreadable dependency is unknown. Metadata changes also alter the Notebook's
whole-file identity; refresh a record only after reviewing that change.

`declared` means the author declared a relationship between these bytes. A passing
record means those bytes are unchanged; it is not proof of a computation, complete
dependency graph, correct figure, or scientific conclusion.

## Optionally observe an explicitly requested command

Ordinary `check`, Studio, MCP and the reusable Action never execute project code.
The separate CLI `provenance run` executes only the command the user supplies:

```sh
paperdelta provenance run training --kind notebook --source analysis.ipynb --cell metrics --input observations.csv --input run_notebook.py --output results/metrics.csv --rationale "Run the reviewed Notebook exporter" --out run-plan.json --command python run_notebook.py
paperdelta provenance accept run-plan.json
```

Place `--command` last; following arguments belong to the external command. Use
your chosen environment's executable and an inspected exporter. Quarto example:

```sh
paperdelta provenance run render --kind quarto --source paper.qmd --input results/metrics.csv --output paper.pdf --rationale "Render the reviewed current source" --out render-plan.json --command quarto render paper.qmd --to typst --no-execute
```

Notebook/Quarto tools are optional external programs, not PaperDelta dependencies.
The command runs in the project directory without an implicit shell. It records
exit 0, start/end times, hashes of local stdout/stderr logs, and the listed inputs'
before/after identities. Notebook code must be the same before and after; saved
outputs may change. Nonzero exit, timeout, changed source code or changed listed
inputs does not create a successful proposal. Default timeout is 600 seconds;
`--timeout` accepts 1–3600 seconds. Logs remain in `.paperdelta/run-logs/`.

`observed_command` distinguishes actual process observation from a declaration.
Acceptance is still separate. Before/after equality is not continuous monitoring;
a no-op command can exit successfully. Editable local records, environment state,
hidden inputs, command arguments and logs require the author's own review. They
do not prove causality or reproducibility. Select records deliberately when sharing
a [portable review](review-bundle.md); logs are not automatically included.

## Generate deterministic result fragments

Choose already accepted numeric binding IDs so the generator reuses their metric,
unit, statistical convention, rounding and display contract:

```sh
paperdelta fragment preview result_table --occurrence table_accuracy --occurrence table_baseline --format markdown --layout table --path generated/results.md --out fragment-plan.json
paperdelta fragment accept fragment-plan.json
```

Use `--format latex` with a `.tex` destination, or `--layout value` with exactly one
binding for a single number. English/Chinese table headings follow the CLI language;
Chinese LaTeX fragments require a Unicode-capable manuscript setup. Generated text
is deterministic for identical inputs, selection order, language and display rules;
the separate record contains its creation time and hashes.

Previewing never writes the destination. Acceptance writes only that reviewed
generated file and its record. It never invents prose or changes a scientific claim.
Adding or repositioning a fragment in the manuscript remains explicit author work.
The generated file is checked for changed inputs, metric/display definitions and
content even if the rounded number remains equal. Refresh with `--replace`; an
existing unrelated file or a manually edited fragment is refused. Use a new
destination to preserve manual edits. Refresh backs up the previous generated file
and configuration. Writes are per-file, not a cross-file filesystem transaction.

## Read the revision list

```sh
paperdelta revisions --baseline submitted-v1
```

The JSON list and offline HTML/text reports identify affected prose, tables,
claims, figures, generation records and fragments. `review_refreshed` means a
bound value already matches changed evidence; it still needs contextual review.
Unknown evidence is listed separately. A false comparative claim is not repaired
by replacing its number. Figure and export tasks ask the author to regenerate and
review the result. Equal values alone never establish an evidence relationship.

Studio's **Notebook, rendered outputs and result fragments** panel supports saved
cell inspection, declaration previews, explicit acceptance, fragment generation
and revision review. Language switches retain fields and selections and invalidate
the old acceptance preview. No command-execution endpoint exists in Studio.

## Compatibility and measured scope

Accepted generation/fragment references require configuration schema **10**.
Configurations 1–9 remain readable and empty new sections are omitted to preserve
legacy identities. New reports use schema **9**, adding optional `provenance` and
`fragments` states and numeric `usage` (`prose`/`table`). Existing snapshots remain
readable. Paper coverage counts still count occurrences, claims and figures;
generation records and fragments have separate states and can make the overall
check fail or remain incomplete. PR summaries expose removed records as removed
coverage, and portable replay retains these declarations and required inputs.

Compatible 1.5 drafts restore through normal review with unchanged inputs. New
records are available through `schema producer-record`, `producer-proposal`,
`fragment-record` and `fragment-proposal`. Hashes provide identity, not signatures.

The [real workflow record](assets/v1.6/workflow-real.json) uses an actual Jupyter
kernel and Quarto 1.9.38/Typst PDF render. It verifies changed upstream data, a
refreshed table and fragment alongside old prose, a false comparison, old figure
and old PDF, plus changed code with unchanged saved outputs. The embedded image's
visual content remains explicitly unverified. [Four browser flows](assets/v1.6/browser.json)
separately cover both fragment formats and languages, previews, acceptance, retained
selections, no execution, stale states and a narrow viewport. These are authored
developer checks, not independent usability or scientific-validity studies.

To reproduce the real process workflow in a development checkout with installed
PaperDelta, install `nbclient==0.10.2`, `nbformat==5.10.4`, `ipykernel==6.30.1` in
that environment and [Quarto](https://quarto.org/docs/get-started/), then run:

```sh
python tools/validate_notebook_workflow.py --out build/notebook-workflow --quarto quarto
```

Use a new output directory. This explicit developer command executes the authored
example; normal checks remain read-only. The [delivery ledger](roadmap.md) records
the 17 named CI jobs and exact public package verification after publication.

Development failures and fixes are retained in the [adjustment record](assets/v1.6/development-adjustments.json).
