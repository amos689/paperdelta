# Incremental checks during ongoing review

[简体中文](zh-CN/v1.9.md)

Version 1.9 reuses unchanged parsed documents and exact metric results during
`paperdelta watch` and Studio sessions. It reads and hashes the current files on
every check. An ordinary `paperdelta check` still performs a full check and is the
comparison oracle for the incremental path.

```sh
paperdelta watch --baseline submitted-v1 --report build/paperdelta
paperdelta watch --no-cache --baseline submitted-v1 --report build/full-check
paperdelta studio
```

## What changes invalidate reuse

Document identity includes the resolved project root, relative file, exact content
hash, format and relevant macro/region configuration. LaTeX include discovery and
ambiguity checks run again, including when a previously missing include appears.
Evidence identity includes the full typed source declaration and fresh content
hash. Source metrics also include their exact selectors, units and statistical
contracts. Derived metrics depend on complete upstream results, including original
evidence locations. Reordering CSV rows therefore updates source line numbers even
when the resulting mean remains identical.

An unrelated source can retain its metric results when another source changes.
Editing one large source invalidates all metrics depending on that source; this
release does not promise row-level incremental parsing. Final reports, manuscript
bindings, claims, coverage, figures, producer records, review notes and baseline
comparisons are rebuilt. Missing or malformed inputs produce current errors;
cached results never substitute for a failed file read.

Files are re-read at the end of a check to detect changes during checking. The
watcher's existing debounce and pending state remain in force, so an old passing
report is not presented as current while inputs are changing. Existing previews
and confirmations keep their independent freshness checks.

Multiple source declarations pointing to the same file must observe the same hash
within one check; differing reads produce `INPUT_CHANGED`. Parsed evidence releases
redundant raw buffers after constructing its read model.

## Memory, copies and compatibility

Each ongoing session owns a process-local LRU cache, normally limited to 4,096
entries and 64 MiB of conservatively accounted retained objects. An entry exceeding
16 MiB bypasses caching. Counts include Python containers and retained native Word
XML trees; unknown native objects also bypass caching. Large CSV parsing can be
bypassed while its much smaller exact metric results remain reusable. Limits are
for retained cache objects, not total process RSS, temporary parsing allocations or
Python allocator retention.

Entries and returned results use separate private copies. Original PDF/Word/Markdown
table metadata is rebound to copied row identities. Mutating a displayed report
cannot poison a later check. Completed Markdown parses release unused parser
closures. The cache stores neither handles, executable manuscript code, accepted
decisions nor persisted files.

Cache identity includes the installed tool, Python and parser dependency versions,
language and decimal context. Restarting or upgrading starts with an empty cache.
Changing the engine identity or explicitly clearing the cache also forces fresh
parsing. No cache migration is needed. Configuration schema 10, report schema 9,
existing commands and native position identities remain compatible; compatible
1.8 drafts are revalidated and restored without accepting them.

## Verification and measurements

The regression suite compares complete reports after excluding only `created_at`:
cold/warm runs, all five manuscript formats in both languages, all five evidence
formats, same-size/same-mtime edits, source deletion/restoration, CSV reorder,
selectors, units, missing/ambiguous includes, baselines, review notes, parser
identity, language, decimal context, bounded eviction and changes during checking.

Run the standalone authored workload measurement with a new output directory:

```sh
python tools/validate_incremental.py --out build/incremental-check --runs 20
```

`--reference-python /path/to/previous/python` optionally runs the same inputs with
an actually installed previous version. The tool checks 20 LaTeX files, a 10 MB
CSV and 500 bindings, and an eight-page PDF with 320 bindings. It alternates full
and warm check order, reports cold cost, median/P95, memory accounting and ten
invalidation scenarios, and compares every report field. Cross-version comparison
also excludes `tool_version`. These are controlled machine measurements, not
independent usability results or latency promises for arbitrary papers.

Final installed-package and browser results are recorded before publication in
the [delivery roadmap](roadmap.md). The approved next Agent release is **2.0**,
following the project's minor-version rollover rule.

## Final installed-candidate results

The exact 1.9 wheel passed 1,010 Windows tests with three POSIX-only skips,
[82 browser cases](assets/v1.9/browser-summary.json),
[13 isolated starts](assets/v1.9/uvx-installed.json), and actual 1.8
[draft restoration](assets/v1.9/upgrade-from-1.8.json) and
[transaction recovery](assets/v1.9/transaction-from-1.8.json).
The strengthened workflow check delays a genuine pre-edit report response and
waits for the edited CSV's hash; a generation increase alone is insufficient.

Twenty repetitions per mode on Windows 11 / Python 3.12.14 / Intel Core Ultra 9
275HX, using installed 1.8 and 1.9 packages on identical authored inputs:

| Workload | 1.8 full P95 | 1.9 full P95 | 1.9 warm P95 | 1.9 cold, one run |
| --- | ---: | ---: | ---: | ---: |
| 20 LaTeX files / 10 MB CSV / 500 bindings | 1.729 s | 1.759 s | 0.853 s | 1.927 s |
| 8-page PDF / 320 bindings | 1.265 s | 1.265 s | 0.246 s | 1.262 s |

The large CSV cold check pays the cache-population cost; this release targets
repeated ongoing checks. Retained cache accounting was 6,892,499 bytes for the
large project and 2,219,161 bytes for PDF, below the 64 MiB budget. Process RSS
after those workloads was 207,343,616 and 208,175,104 bytes; peak RSS was
267,542,528 bytes. The cache budget is not a whole-process memory limit.
All 20 full/warm reports per workload, the previous-version results, and all ten
invalidation scenarios agreed on every compared report field. Raw samples,
loaded previous-version code identities and comparison limits are in the
[installed measurement](assets/v1.9/performance-installed.json).
[First failures and repairs](assets/v1.9/development-adjustments.json) remain
available, including the interrupted platform run. Release still requires the
exact candidate's 17 remote jobs and verified public downloads.

The PyPI description was subsequently corrected and translated. The
[archive comparison](assets/v1.9/wheel-provenance.json) confirms that only the
metadata description and its checksum record changed; all 125 other wheel files
and dependency headers are identical. Measurements keep the original measured
archive hash. The final archive undergoes a separate installed-package check.
