# Review the evidence behind an Agent proposal

[简体中文](zh-CN/v2.0.md)

Version 2.0 gives direct, staged and batch proposals a shared evidence review.
The CLI JSON preview and Studio display the same declared experiment identity,
source bytes and original manuscript positions. The version follows the project's
minor-version rollover rule: 1.9 is followed by 2.0. Configuration schema 10,
report schema 9 and the existing 22 MCP tools remain compatible.

## What to inspect

For each proposed binding, inspect the following together:

| Review field | What it establishes |
| --- | --- |
| Source path, exact hash, format, sheet/range or JSON pointer | Which local evidence bytes the declaration reads |
| Column types, primary key and selectors | The declared experiment identity, including string IDs such as `001` |
| Expected count, seed column and seed set | Whether the declared selection contains the required records |
| Source unit, reduction and derived dependencies | How those selected values produce the result |
| Original position, manuscript hash and surrounding context | Where the proposed statement appears in the actual source or native document |
| Display rule, actual value, expected value and diagnostics | The deterministic outcome under that declaration |
| Provided rationale | An assertion to review, not a separately verified scientific fact |

The structured `review` uses `review_schema_version: 1`. Its
`identity_status: requires_author_review` and
`rationale_status: unverified_assertion` keep declarations distinct from computed
facts. Two different checkpoints can produce the same mean. A matching number
does not select the right checkpoint. Conversely, a stale number in the paper
can be the correct location to bind even when the comparison reports a mismatch.

Evidence samples explicitly report `records_total`, `locations_total` and
`truncated`. Final proposals normally show ten records; draft reviews show five.
The declared path, selectors and source coordinates remain available. Studio can
expand the complete metric evidence. For a saved proposal, the full CLI preview is:

```sh
paperdelta bind --proposal mapping-proposal.json --format json
```

The returned `preview.metrics` retains all selected records. The shared review
links to that evidence; it does not silently present a sample as the complete
selection. Save Agent-returned `proposal_json` verbatim before invoking the CLI.

## Correct a staged declaration

`start_mapping_session` supplies the current schemas. Continue with the returned
session ID and revision; use only the returned `allowed_actions`. Each response
includes the current stage guidance and the evidence available so far.

If a successful stage declared the wrong source or unit, use the
`advance_mapping_session` tool with `action: "undo"`, empty `arguments` and an
explicit reason. This retracts the last successful stage. A later location stage
must be undone before an earlier metric can be retracted. At most four undo
actions are permitted within the existing sixteen-action limit. Three invalid
actions still exhaust the error budget. An invalid action preserves the last
valid draft.

Undo retains every previously observed input hash, including a source no longer
in the draft. It cannot make changed files fresh. Expired, stale and terminal
sessions must be restarted. When evidence does not justify the experiment
identity, unit, complete records or derivation, `abstain` records a nonempty
reason. Exhausting a budget is an incomplete result, not a successful abstention.

## Review in Studio

Run `paperdelta studio`, open binding review and import the saved proposal JSON.
Inspect the experiment identity, original context and selected records. Choose
the bindings to accept, then explicitly confirm. Importing a proposal does not
select or accept its bindings. Switching between English and Chinese preserves
the selected bindings and clears confirmation. A stale import cannot reuse an
earlier confirmation or acceptance action.

Compatible persisted 1.9 Studio drafts are revalidated when restored. Restoration
does not accept them. Normal checking and all MCP tools remain read-only with
respect to manuscripts; no mapping tool executes paper code or writes a review
attestation.

## Evaluation scope

The [preregistered protocol](../validation/mapping-v5/PLAN.md) separates machine
acceptance from real Qwen3-8B Q4_K_M inference. Twelve old tasks are a regression
on already observed inputs. Twenty-four new authored tasks were frozen before
product tuning: twelve development tasks and twelve held-out inference tasks,
each with eight mappings and four required abstentions. Both languages and all
five manuscript formats are represented.

The new tasks are authored synthetic cases, not a blind evaluation or an
independent user study. Native positions were generated with the existing 1.9
parser and visually checked on original Word/PDF inputs. Held-out means their
model outcomes were excluded from tuning until the chosen implementation and
prompt were frozen. The [study record](../validation/mapping-v5/README.md) preserves
the protocol, original inputs, raw responses, costs and first failures. Evaluation
does not grant an Agent permission to accept bindings.

## Results and release acceptance

The first held-out real-model run completed 1/8 mappings and explicitly abstained
on 2/4 required-abstention cases. This small authored study does not establish
reliable autonomous mapping. The selected second development implementation
reduced invalid actions from 33 to 21, while complete mappings fell from 1/8 to
0/8. The shared review and typed contracts make declarations inspectable; they do
not prove the model chose the right experiment. All first failures, both rounds
and the selection made before held-out inference remain in the
[study results](../validation/mapping-v5/README.md). No binding was accepted during
inference, and abstention reasons have no independent semantic assessment.

The [local acceptance receipt](assets/v2.0/local-acceptance.json) identifies the
exact installed 2.0 wheel. It passed 1,021 Windows tests with three POSIX-only
skips, 92 browser cases and 13 isolated starts. Actual public 1.9 drafts and
transaction recovery were exercised, preserving inputs and requiring a fresh
review. Five-format bilingual flows include language changes and stale imports.
The [browser summary](assets/v2.0/browser-summary.json) and
[development adjustments](assets/v2.0/development-adjustments.json) retain the
original failures and explain each correction.

All 60 recorded model cases passed frozen implementation replay, and 13 authored
reference/adversarial controls passed without model calls. Those checks establish
record consistency and deterministic behavior, not additional model successes.
Final publication additionally requires all 17 named cross-platform CI jobs,
matching public distribution/evaluation downloads and a fresh public install
running five formats in both languages. Publication is recorded separately in
the [roadmap](roadmap.md).
